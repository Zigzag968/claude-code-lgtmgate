# Architecture

## Bird's eye view
A Claude Code plugin. The Lead runs `/lgtmgate:deliver <issue>`; the workflow drives the agents
(Theo diagnose → Sam plan → Nick implement + PR → Morgan review), each in the issue's worktree, and
returns one status. A human merges through `scripts/lead-merge.sh`. Direction: `VISION.md`.

## Code map
- `workflows/deliver-pipeline.js` — the engine: stages, statuses, the design step. All agent calls go
  through `callAgent`.
  Invariant: the three R1 counters (agent calls outside `callAgent`, `simulate.*` seams, regex on
  agent output outside parser markers) never rise against `main` — `scripts/guards.cjs`.
- `agents/*.md` — personas. Invariant: the rules shared with the engine prompts are byte-identical
  (`sam-parity` in `scripts/guards.cjs`).
- `commands/` — `/lgtmgate:deliver`, `/lgtmgate:init`: the Lead's runbook.
- `hooks/` — session guards (destructive git, unchecked merge, worktree cleanup, stale runs).
- `scripts/` — `guards.cjs`, `lead-merge.sh`, `run-offline.cjs` (fixture replay), `run-flow-suite.cjs`.
  Invariant: a PR merges only through `lead-merge.sh`, which bumps the version at merge.
- `templates/` — flow suite and canonical guards run in CI; files copied into consumer repos.
- `fixtures/incidents/` — raw runs replayed offline. Invariant: an engine bug is fixed with a fixture
  red on `main`, green on the branch.
- `plugins/backlog/` — a separate plugin for issue triage.

## Where new code goes
| You need | Put it in |
|---|---|
| a new outcome of a run | the status table of the engine (one-way door: stop and ask) |
| a shell side effect or a probe | today `callAgent`; target (E2): the single `probe-run` port |
| a new check on a PR | an acceptance item, generated by the engine |
| a fix for an engine bug | `fixtures/incidents/<issue>-*.json` first, then the fix |

## Cross-cutting
- Config contract: `.claude/pipeline.config.json` keys change additively only.
- Channels: `stable` (pinned) and `beta` (`main`), see `MAINTAINING.md`.
